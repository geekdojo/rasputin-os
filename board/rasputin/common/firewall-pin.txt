# firewall-pin.txt — the ONE firewall release this OS image bakes a manifest for.
#
# Format: exactly one non-comment, non-blank line holding a bare CalVer version
# — no leading "v", because the firewall's release tags are bare CalVer
# (2026.09.4-dev.127, not v2026.09.4-dev.127) and the release asset URL is built
# from this line verbatim. Anything else fails the build in post-build.sh.
#
# WHAT IT IS FOR
#
# post-build.sh fetches this release's manifest.json + manifest.json.sig,
# verifies the signature against the image's own trust root, and bakes both into
# the rootfs at /usr/share/rasputin/firewall/. The control plane serves that
# baked descriptor from GET /api/cluster/firewall-image when it cannot reach
# api.github.com — which is exactly the greenfield bring-up the no-DHCP fallback
# address exists for: a controlplane on 192.168.1.2/24 with no default gateway
# has no internet, so an unbaked image leaves the operator unable to flash the
# firewall that would give it one. geekdojo/geekdojo-brain#595.
#
# WHY A PIN AND NOT "LATEST AT BUILD TIME"
#
# "Latest" is the shape that burned 2026.09.2: the firewall build followed an
# unversioned Snort3 rules URL, Talos republished between a green pre-flight and
# the tag build, the SHA mismatched, and because release tags are immutable the
# version was lost and the line re-cut as 2026.09.3 (geekdojo/geekdojo-brain#208,
# rasputin-openwrt-firewall PR #48). A build-time "latest" also makes the image
# non-reproducible and records nowhere which firewall release a given OS image
# actually trusts.
#
# SO THIS LINE IS A COMPATIBILITY STATEMENT, NOT A BUILD-TIME ACCIDENT:
# *this OS release is paired with this firewall release.* It moves only
# DELIBERATELY, as part of a release chain, in the same OS pin PR that moves
# the agent/api pins -- never as a drive-by refresh to "pick up the newest
# firewall", and never automatically. Bench validation of the pair follows the dev build, as it
# always does; the pin does not wait for it.
#
# THE RULE -- INVIOLATE (Bryce, 2026-09-27): "dev only bakes dev. Stable only
# ever bakes stable." It is not a choice and is not asked per release.
#
#   DEV    chain: CP dev release -> firewall dev build -> ONE OS PR pinning
#          agent/api to that CP dev release AND this line to THAT chain's
#          firewall dev release (YYYY.MM.MICRO-dev.N).
#   STABLE chain: a stable OS X bakes the stable firewall X, which therefore
#          publishes BEFORE this pin moves (rasputin-os-release skill,
#          section D step 3). A stable OS pinning a -dev firewall would hand
#          every offline greenfield install a dev firewall.
#
